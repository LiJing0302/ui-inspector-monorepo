# 重合节点：人工验收方案评估

结论：识别重合层、帮助验收人员检查一个视觉元素，是合理方向。现已将单侧检查与人工 diff 接入同一套属性来源解析，替换旧的「并集、冲突取上层」路径；该解析汇总可确认的属性，不重建最终视觉效果。

初次评估完成了代码核对与合成数据复现；随后已按用户要求修正重合判据，尚未执行新的真机采集。用户截图证明当前提供了重合层入口；下文数值案例由当前函数实际运行得到，不代表截图对应页面的完整原始数据。

## 已落实的判据修正（2026-10-15）

用户明确要求不允许 0.5 单位误差。现已取消该容差：同父且合格的节点，只有 x、y、width、height 四项严格相等才属于重合组，不对数值取整，也不豁免浮点残差。

人工检查的 App 节点优先比较 SDK 留存的原始 `pixelRect`；它随 `toRenderNode` 传递，避免逻辑值归一化取两位小数后将不同边界当成相同。旧快照与设计稿使用已有逻辑矩形严格比较；有／无原始像素元数据的节点不混组，避免旧节点把两个不同的原始矩形串成同组。另一处 AI 视图的重合判据也同步改为四项输入严格相等；其非重合类型的视觉分组规则未调整。

0／0.4／0.8 的三个偏移节点现在分别独立，切换选择不再产生 2／3／2 的候选组。下面其余分析保留首次评估时的证据，当前实现见下一节。

## 样式汇总落地（2026-10-15）

- `lib/elementInspection.ts` 分别解析设计稿与 App 的严格重合组，保存真实 anchor、成员与逐属性来源。CanvasBoard 传入完整原始节点池，不受 AI 显示筛选影响；不再生成合成的 selected 节点。
- 单侧汇总、两侧人工 diff 和问题证据共用解析。只有已知无绘制壳可排除；未知通道和不同属性值（包含明确 0）均显示「多层待确认」。index／z 不用于裁定属性归属。文本与字体、描边颜色与宽度作为相关字段核对，避免跨层拼装。
- 几何始终读取真实 anchor；目标值仍按页面宽度比例计算。多层复杂填充、透明与自绘内容不声称获得合成颜色或最终轮廓。
- 面板提供「元素汇总 / 单层属性」，在原始层列表点选会进入对应侧单层检查。切换组内成员保持组身份；新配对或新组默认回到汇总。
- 打开问题表单时冻结关联原始节点、两侧检查范围、组成员及逐属性候选／冲突状态。之后换层或切换检查范围不改变待保存证据。

回归用例覆盖壳＋渐变层、未知上层、明确零冲突、独立两侧分组、文本／描边关联、透明／自绘填充、显示小数相同但原始值不同的冲突。Electron 集成覆盖插件导入、SDK 上传、落盘、两侧汇总及证据持久化。仍需宿主真机验证实际绘制与采集通道完整性。

## 首次评估时的行为与断点

1. `CanvasBoard.tsx:749` 对主动侧选中节点调用 `stackOf`，找出同父、可见、有面积、矩形接近的兄弟。`stack.ts:49` 的容差是每项坐标 0.5 个逻辑单位，并非注释所说的严格相等。
2. `CanvasBoard.tsx:765` 生成重合层列表及 `mergedSelected`，App 样式通过 `mergeAppNodes` 聚合。`stack.ts:236` 用最末层的节点作为对象基础，再摘取各层盒样式、文本样式及文本内容。它返回的是合成视图，没有回写原始节点树。
3. `CanvasBoard.tsx:277` 的 `comparison` 使用真实选中的 design/App 节点，没有使用聚合视图。
4. `NodeInfoPanel.tsx:245` 的人工 diff 从 `comparison` 生成字段；`:325` 的对比分支也没有重合层列表。单侧分支在 `:336` 才展示列表和聚合后的属性。

因此，仅修改单侧 `selected` 的内容，不会修复 diff。当前聚合又只根据「主动侧」生成，不能直接把这一份聚合结果同时供给两侧比较。

## 当前设计的合理部分

- RN 一个可见按钮可以由渐变层、点击壳、文本层共同构成。让验收人员只检查命中的某个原生层，容易把「另一层持有的圆角」误认为没有实现。
- 保留原始节点和树形是正确的。检查重合层无需修改 SDK 采集结构，也无需把节点与任意源码属性逐一绑定。
- 已有「此处有 N 个元素」列表值得保留：它能帮助定位属性持有层，也能解释为何单个节点没有完整外观。

## 不能直接沿用的假设

**同位置不能证明同一组件。** 它也可能是遮罩、状态层、半透明覆盖层。父子同框、部分重叠与完全同框的兄弟也应分开处理。

**独立节点的样式不是 CSS 继承。** 上层没有圆角字段，不意味着它继承下层圆角；有不透明填充的上层可能遮住下层。两个半透明填充的最终颜色也不是简单取上层颜色。圆角还可能分别作用于背景绘制和子内容裁剪。

**index 不能单独证明绘制顺序。** `stackOf` 只按 index 排序，原始 AppNode 虽然带 z/elevation，但该排序没有使用它们。即使顺序可靠，也仍需处理透明度和裁剪，不能把任一上层属性当作最终外观。

**缺失和零不能混为一谈。** 已采集的无样式壳，与样式通道完全未知的层，不是同一种证据。当前合并能保留部分三态，但一旦下层提供值，就会忽略上层通道缺失带来的不确定性。

**近似重合会使组不稳定（已修正）。** 原先按选中节点为中心查找，0、0.4、0.8 三个偏移量会形成不同成员集；切换列表里的层，可能连「这个元素由哪些层构成」都发生变化。尺寸有差异时，合成对象还会取最末层的几何。

## 已运行的复现

运行现有 `stackOf`、`mergeAppNodes`、`buildManualFields`、`toRenderNode`，七个场景的断言均通过：

| 场景 | 当前代码结果 | 说明 |
| --- | --- | --- |
| 下层圆角 7.67，上层 style=null 的点击壳 | 原始节点 diff 为 0 dp／偏差；聚合视图为 7.67 dp／一致 | 确认单侧与 diff 的数据来源断点 |
| 上层有不透明背景，但没有圆角采集通道 | 聚合借用下层 7.67 并提示一致 | 没有足够信息证明上层最终轮廓，不能据此确认外观一致 |
| 上层 style=undefined，整份样式未知 | 同样借用下层并提示一致 | 不能把未知层当成已知无绘制的壳 |
| index=0、z=10 的红层与 index=1、z=0 的蓝层 | 摘取蓝色 | 聚合只使用 index，未考虑原始 z 信息 |
| 同父节点 x 偏移为 0／0.4／0.8 | 修正前组成员数 2／3／2；严格比较后为 1／1／1 | 已取消近似重合，保持各节点独立 |
| 上层明确四角为 0，下层四角 7.67 | 摘取 0 | 当前并非无条件漏掉零值；问题是冲突裁决依据不足 |
| 选中下层，但调用 mergeAppNodes | 返回对象 id 是最末层；原始节点未被修改 | 合成视图的身份与选中层可能不同，不能冒充一个真实节点用于证据 |

## 方案比较

| 方案 | 收益 | 问题 | 建议 |
| --- | --- | --- | --- |
| 只允许切换原始层，始终逐层 diff | 每个数来源明确 | 验收人员需要理解 RN 层级，一个按钮要反复比多次 | 保留为详情入口 |
| 给 diff 接上现有 mergeAppNodes | 修复截图中常见的空壳＋渐变层问题，改动小 | 会把不确定的遮挡、缺失通道和属性冲突变成单一值 | 不作为完整方案 |
| 原始层保留，统一汇总属性并显示来源及冲突 | 常见场景一次检查完成，复杂情况可展开确认 | 需要一个供单侧与 diff 共用的属性解析入口 | 推荐 |
| 在 SDK 或存储层合并节点 | 表面上减少节点数量 | 影响身份、树形、选择和既有配对；仍无法解决视觉合成 | 不采用 |

## 推荐的产品流程

点选后仍选中真实节点。存在严格同框的兄弟时，面板展示「由 2 层组成」，默认展示可确认的属性汇总，现有层列表收在详情中。单侧检查与两侧 diff 使用同一份属性解析结果。

以用户截图的结构为例：如果 ReactViewGroup 已确认不绘制盒外观，LinearGradientView 持有完整圆角，那么圆角行展示「7.67 dp」，附简短来源「渐变层」。宽高与间距继续读取明确的真实节点边界，不计算多个矩形的并集，不取最大圆角，也不改变此前确认的设计稿宽度比例公式。

两层均有圆角且不同，或者有绘制层未采集圆角时，显示「多层待确认」并在展开后列出各层数值。该行不参与一致／偏差结论。若用户要检查某一原生层，可在已有列表中进入单层详情；单层详情明确写明检查范围。无需新增项目配置或逐属性源码映射。

如果所有相关通道完整且提供相同数值，可以展示该值；但这只表示各层属性一致，仍不等于已重建外观。渐变、透明叠加和裁剪继续依赖人工看图。

## 实现边界与验收条件

1. 两侧分别解析自己的候选组与属性来源，避免使用仅针对主动侧的 `mergedSelected`；单侧面板、diff、问题证据共用解析结果。
2. 汇总结果单独携带选中 anchor、成员 id、属性持有层和完整性／冲突状态；不再用一个混合后的 AppNode 冒充真实节点。来源仅在多层时显示，完整 id 可放详情和问题证据。
3. 自动汇总先限于同父、最终原始像素矩形一致且外观来源可确认的情况。旧数据没有 pixelRect 时也必须四项逻辑数值严格一致；不引入近似重合提示或浮点误差豁免。分组以固定键建立，切换成员不能改变组本身。
4. 壳的判定必须有已采集的「自身不绘制该类外观」证据，不能由 className、缺少字段或与设计值接近推断。明确 0 是有效值，未知状态继续保留；描边宽色需对应同一绘制层，文本内容及字体属性也需来自对应文本层，不能任意拼装。
5. 多个有绘制能力的候选、可能遮挡的层或不同数值，不以 index 自动裁决。不确定时保留候选和人工切换入口，避免为此先做一套原生合成引擎。
6. 父子、近似重合和局部覆盖继续用原始层级检查。确有需求后再为「已证明透明且只有一个有效子内容」的包装链增加特定解析，不把任意相邻节点一并吸收，也不直接复用范围更宽的 AI 归并策略。
7. 后续落地需验证：截图中的空壳＋渐变层在单侧和 diff 中同值；未知上层不误判；明确零与多个值不丢失；换层不改变组；原始 id、几何、间距和设计推算目标不变；问题记录保存本次实际使用的属性来源且打开表单后保持冻结。

建议优先完成共享属性解析与常见的无绘制壳场景，再处理更广泛的组合结构。这样能解决人工验收的实际断点，同时保留复杂重叠场景所需的信息。
