# 为什么锁定的几乎都是文本 —— 图形/图片配不上的实测归因

> 样本：`盲盒抽奖 / 10年管家开通前`（2026-09-17 01:08 导出包，含装好 SDK 修复后的采集）
> 设计稿 609 节点（375×1261）· App 527 节点（360×792，vivo V2454A）
> 引擎：v2 锚点优先（L2 文本锚点 → L3a 祖先投票 → L3b 兄弟分配）
> 复核命令：`npm run probe:match -- "<导出包>"`、`SM_MATCH_TRACE=1 …`、见文末「怎么复现」

---

## 一、现状：79 条锁定，58% 是纯文本对

| 组尾类别（设计 ↔ App） | 条数 |
|---|---|
| text ↔ text | **46** |
| box ↔ box | 29 |
| graphic ↔ graphic | **3** |
| box ↔ layout | 1 |
| **合计** | **79**（matched 48 / ambiguous 31） |

按来源：`text-anchor 40 · sibling 27 · ancestor-vote 8 · text-disambiguated 3 · text-aggregate 1`
→ **44/79（56%）直接来自文本锚点**，另外 35 条里 30 条是盒子。

设计侧 required 438 个的归宿，按意义类别拆开才是关键：

| 类别 | required | 配上了 | 进过矩阵没配上 | **静默丢失**（从没进过矩阵） |
|---|---|---|---|---|
| text | 69 | 45 | 1 | 23 |
| **graphic** | **213** | **3** | 18 | **192（90%）** |
| box | 156 | 22 | 39 | 95 |

**一句话结论：图形/图片配不上不是「分不够」，是 90% 的它们从来没被比较过。**
`MATCH_THRESHOLD 0.38` / `SIBLING_MIN_SCORE 0.7` 这两个阈值不是瓶颈 —— 分母上根本没有它们。

## 二、四条原因（按影响排序）

### R1 · 引擎只有「文本」这一条直接证据通道，其余全靠扩散

L2 只认文本（`resolveTextAnchors`）。图形/图片要配上，必须**先锁住它所在的容器**，再由容器把子节点分配掉。
而扩散的播种条件是「锁定配对的**组首有子节点**」：

- 79 条锁里 **47 条是叶子**（46 文本 + 图形），`enqueueContainer` 走到 `designTarget.childIds.length === 0` 直接 return —— **锁上了也播不动**；
- 实际能播种的只有 **32 条**（ancestor-vote 8 + sibling 24），跑出 **29 个容器步**。

也就是说：**一条文本锚点只能往上产生投票，不能往下扩散**。

### R2 · 容器锁太少：投票要求 ≥2 票，扩散又只从容器出发

`VOTE_LOCK_MIN_COUNT = 2` —— 一个容器需要子树里至少 2 个已锁文本锚点指向同一个 App 祖先才上桌。
本轮只有 **8 个容器**靠投票锁定。于是整张扩散树只有 8 个根 + 24 个二级分支。

trace 实测这 29 步的收支：

| 指标 | 数值 |
|---|---|
| Σmin(rows, cols)（理论上限） | **67** |
| 实际产出的兄弟分配 | **27** |
| 有剩余的步数 | **24 / 29** |
| 一侧组数为 0 的步数 | **3**（`12484 rows=11 cols=0`、`12560 rows=11 cols=0`、`12368 rows=0 cols=1`） |

根步最能说明问题：**设计根 9 组 ↔ App 根 35 组**，一次最多只能配 9 对，剩 4 组没配上、38 个 App 组没人要。
`cols=0` 那三步则是「对侧子节点已被更早的步骤吃光」—— 一条子树从此整块作废。

### R3 · 硬门控 `salienceAffinity` 把「图形 ↔ 盒子/透传壳」判 0，而这正是图标的必然形态

```ts
const firstBranches = first === 'box' || first === 'layout';
const secondBranches = second === 'box' || second === 'layout';
if (firstBranches !== secondBranches) return 0;   // ← graphic ↔ box / layout 一律死刑
```

拿设计侧 228 个 required 图形/图标/图片，去 App 侧找**同位置同尺寸**（互为对方矩形 ≥60%）的节点，只找到 65 个；这 65 个的对侧是：

| 对侧类别 | 条数 | 结果 |
|---|---|---|
| `layout`（`PathView` 系） | **40** | 门控 = 0，永远配不上 |
| `box`（`ReactViewGroup` 包装） | **15** | 门控 = 0，永远配不上（另有 1 个本节点已配上，是靠组内别的层配上的） |
| `graphic` | **9**（其中 2 已配上） | 相容 |

一个具体样本（几何几乎完美，只差类别判定）：

```
设计 design:1755:12362 [图标图层] 24×15 @(147,427)
  ↔  App PathView (layout) 23×14 @(141,410)   ← 141×1.0417 = 146.9，y 完全一致
     它属于 SvgView (graphic) 30×30 @(137,397)
```

同一枚 30×30 的矢量图标，两侧其实**逐层对齐**（24×15↔23×14、10×7↔10×7、3×6↔3×6），但：

1. **矩形对得上的那一层是 `PathView`，被判成 layout** —— `NodeCollector.hasVisualContent` 只认 `SvgView` 根、`ImageView`/Drawee、渐变、TextView、背景色/描边/背景图；`com.horcrux.svg.PathView` / `CircleView` / `RectView` 全部 `hasVisualContent=false`、`isSvg=false` → Mac 侧落入「无有效子节点且不画东西」分支 = `layout` → 与设计稿 graphic **门控判 0**。
   实测：`PathView` 66 个（62 个落进 context 档、**既不参与覆盖率，也配不上任何图形**）、`CircleView` 9、`RectView` 2、`MaskView` 2、`DefsView` 11、`RadialGradientView` 8、`ClipPathView` 4。
2. **整体对得上的那一层是 `SvgView`（被判成 graphic）**，但它对应的设计侧是那个**图标 Frame（box）** → 门控同样判 0。
   根因是 `SvgView` 的唯一直接子是 `0×0 的 GroupView`，而 `effectiveChildren` 会把零尺寸子节点过滤掉 → SvgView 看起来「没有有效子节点」→ 被当成叶子图形。

App 侧真正的图片（`isImage=true`，52 个）同样被门控挡住：

| 状态 | 条数 | 对侧是什么 |
|---|---|---|
| 从没进矩阵 | 30 | 18 无同尺寸节点 · 8 `box[FRAME]` · 4 `graphic[RECTANGLE]` |
| 进过矩阵没配上 | 20 | 9 无同尺寸节点 · **8 对侧是 `box[GROUP]`** · 1 `layout[FRAME]` · 1 `box[FRAME]` · 1 `graphic[VECTOR]` |
| 已配上 | **2** | `box[GROUP]` |

「图片配不上图片」的原因很直白：**设计稿那边放的是 FRAME / GROUP（有子节点 = box），App 这边是一个叶子 ImageView（graphic）** → 判 0。反过来（设计稿一张图片图层 ↔ App 侧一个 ViewGroup 包两层）也一样。

### R4 · 粒度/尺寸不可比：163/228 的设计侧图形在 App 侧同位置没有同尺寸节点

- 65 个：有同尺寸对侧节点（上面那张表）
- **161 个：被 App 侧一个更大的节点整块包住** —— 对侧是 graphic 77 · layout 57 · box 26 · text 1
- 1 个被拆成更小节点、1 个位置错开（有重叠但尺寸对不上）
- 0 个：App 侧完全没有重叠节点

这 161 个里，很多是「设计稿把一个图标拆成 6 个图层、App 侧是一个 30×30 的 SvgView」这类**粒度差**，或设计稿一个 4×7 的小图形落在 App 侧一张大图里面。它们被算成 `required`，于是稳定产出 missing 噪声 —— **这不是缺陷，是口径问题**。

## 三、对照实验：每种改法各能捞回多少

用临时补丁改引擎跑同一份导出包（改完已还原，`core.ts` 校验和不变），四种情形对照：

| 情形 | matched | ambiguous | missing | extra | design required 覆盖率 | 静默丢失 |
|---|---|---|---|---|---|---|
| 基线 | 48 | 31 | 523 | 448 | 16.0% | 310 |
| ① 扩散改从文本锚点的**祖先**播种 | 53 | 41 | 508 | 433 | 18.7% | **274** |
| ② 门控放开（graphic↔box/layout 不再判 0） | 46 | 43 | 513 | 430 | 17.1% | 315 |
| ③ ①+② | 52 | 74 | 474 | 385 | **24.9%** | 259 |

读法：

- **① 只改一行、不放松任何判据**，靠把扩散树真正铺开：锁 79→94，静默丢失 −36。代价是多 10 条 ambiguous（要人看）。
- **② 单独放开判据收益小、还略微恶化静默丢失**（310→315）：因为链没修好，多出来的候选在错误的层级上互相抢。而且 `matched` 从 48→46（两条本来 confirmed 的降成 ambiguous）—— 说明门控确实是那两条的护栏，**不能简单回退**（09-16 修「设计侧 7 个子节点的盒子配到 App 侧一个叶子图形、下推当场断掉」用的就是这个门控）。
- **③ 两者都做**才有质变：锁 79→126，覆盖率 16.0%→24.9%。

## 四、建议（按性价比排序）

| 优先级 | 动作 | 预期 | 代价 / 陷阱 |
|---|---|---|---|
| **P0** | `matchDocuments` 的播种改用「组首的祖先容器」而不是组首本身（叶子才向上取一层） | 覆盖率 +2.7pt、静默丢失 −36、不动任何判据 | 多出 ~10 条 ambiguous；要点：只向上取**一层**并跳到最近的 `box`，别跳到根（会重演「45 个锚点全投给根」） |
| **P1** | SDK：把 `com.horcrux.svg.*` 的绘图子节点认成自绘（`hasVisualContent=true`，或新增 `isVector` 标志）；同时让零尺寸的中间层（`0×0 GroupView`）不遮挡父节点对子节点的「有效子节点」判定 | 直接解锁 40 个「逐层对齐却门控判 0」的图标 | ⚠️ 这些节点会从 `context` 变 `required`：覆盖率分母 +~85，missing 会先涨。**必须同时做「同一父下多个图形叶子聚合成组」的匹配口径**，否则只是把静默丢失换成了显式 missing |
| **P2** | 门控按证据分档：`graphic ↔ box/layout` 不再一刀 0，改成「几何达标 + **视觉证据达标**（pHash/SSIM）才给分」 | 捞回 15（box）+ 若干 layout 图片配对 | 会动到既有 matched 集合（实验里 2 条降级）；必须保留视觉闸门，否则「盒子配叶子」老错配复发 |
| **P2** | `required` 口径：对「设计稿粒度更细」的图形（R4 那 161 个）不报 missing | 523 missing 里能砍掉一大块噪声 | 需要一条可验证的粒度判据（例如「被对侧更大的节点以 ≥90% 面积包住」），否则会把真缺失也吞掉 |
| P3 | 修 `cols=0/rows=0` 那 3 步代表的「先到先得吃光对侧」问题（当前是 FIFO 贪心） | 解锁 `12484` / `12560` 两棵子树（各 11 组） | 要引入回溯或全局分配，复杂度上一个台阶；建议等 P0/P1 落地后重测再决定要不要做 |

**不建议**：调 `MATCH_THRESHOLD` / `SIBLING_MIN_SCORE`。192/213 的图形压根没进矩阵，调阈值只是让进过矩阵的那 18 个更松，收益可忽略、噪声直接上来。

## 五、怎么复现（本次分析用到的四条量测）

1. **构成**：`npm run probe:match -- "<导出包>"` → 看「锁定配对的来源」「归宿表」；加 `--list` 看全部配对。
2. **队列收支**：`SM_MATCH_TRACE=1 npm run probe:match -- "<导出包>" | grep -E '^\[L3b'` → 每步 `rows/cols`、`[L3b:leftover]` 未分配组。
3. **两侧分类口径**：按 `participation === 'required'` × `salience` 交叉统计，取 `trace.scopedDesign/scopedApp` 区分「进过矩阵」与「静默丢失」。
4. **同一块东西的对侧类别**：取设计侧节点与 App 侧节点「互为对方矩形 ≥60%」（注意 App 侧矩形要乘 `design.width / app.width` —— 漏乘缩放会得到完全错误的结论，本次第一版就栽在这），再看对侧的 `salience` / `className`。

> ⚠️ 本报告的结论来自**单页实测**。机制性问题（R1/R3）与该页无关，但 R4 的具体比例（163/228）会随设计稿的图层组织方式变化。
