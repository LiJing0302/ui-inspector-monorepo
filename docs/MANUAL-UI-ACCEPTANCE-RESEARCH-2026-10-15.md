# 人工元素 UI 验收：公开讨论、竞品与平台方向

调研日期：2026-10-15。范围：Mac 验收端检查移动端 App 的元素、尺寸、间距和圆角。暂不设计叠图或 AI 验收流程。本次查阅公开文档、社区 issue 和 Lookin 的测量源码；没有安装并实测这些竞品。

## 1. 可以先确定的方向

**人工元素检查可以继续推进。主流程应检查“经双方认可的适配规则转换后，设备上的元素是否符合设计要求”，而不是要求设计文件的 px 数字与截图 px 数字相等。**

本次核实的工具提供了两块可组合的能力：

- Zeplin：先约定设计密度和目标平台，输出开发使用的 pt / dp / CSS px。
- Lookin、Reveal、Android Studio Layout Inspector：从运行中的 App 读取视图结构、属性和布局信息，辅助人工查问题。

在所查资料中，**没有发现覆盖任意 Figma 设计、任意移动适配策略，并给出通用“相差多少像素即合格”的行业标准**。这里是本次调研的证据边界，不能据此认定市场上没有其他方案。

对本平台的建议是：**借鉴 Zeplin 的单位配置、Lookin 的元素测距、Layout Inspector 的属性检查，再补上设计与实机之间明确的目标值和人工结论。** 不必等待一个能复现所有布局引擎的像素模型才恢复人工验收。

## 2. 网上有没有相同问题：有，而且成因不止一种

### 2.1 React Native 官方：任意精度布局与最终像素格不是同一件事

[React Native 0.81 PixelRatio 文档](https://reactnative.dev/docs/0.81/pixelratio) 的 “Pixel grid snapping” 说明：

- JavaScript 和布局引擎使用任意精度数值；写入原生元素位置与尺寸时才取整。
- 取整相对于根节点，而不是逐层相对父节点，以避免累计误差。
- 混用已取整和未取整的数据会累积误差；甚至可能让 1px 边框消失或变成两倍宽。
- `roundToNearestPixel(8.4)` 在密度 3 下约为 `8.3333` 逻辑单位，对应 25px；返回值不要求是整数逻辑单位。

**含义：** 面板出现小数不自动说明开发写错；也不能把所有 1px 差异统一忽略。

[Yoga 配置文档](https://www.yogalayout.dev/docs/getting-started/configuring-yoga) 的 “Point Scale Factor” 进一步说明：布局点到物理像素的映射由配置指定，设为 0 可以关闭像素格取整。文档还解释了版本和 Errata 配置会影响布局兼容行为。因此，同一套期望值算法需要声明适用框架和配置。

### 2.2 社区案例：相邻元素产生细白缝

[RN #24414：Android 相邻视图的像素取整问题](https://github.com/react/react-native/issues/24414)

报告者在 Android `PixelRatio = 2.625` 的模拟器上，发现理论上紧邻的元素之间出现细缝，而 iOS 没有。提供了代码和截图，使用 RN 0.59.4。

**可借鉴：** 非整数密度、相邻边界和不同布局位置都应进入校准样本。该 issue 因长期无活动关闭，不能把“Closed”解释为已修复，更不能据此断言你们当前版本有同一个 bug。

### 2.3 社区案例：都写 height 15，Text 却比 View 多 1px

[RN #42140：相同高度的 Text 与 View 实际渲染相差 1px](https://github.com/react/react-native/issues/42140)

报告者在 RN 0.73.1 / Fabric、密度 3.5 下，给父 View 和子 Text 都设置 `height: 15`，在特定顶部偏移下，Text 多渲染 1px，边框还会被裁剪。页面提供复现项目。

**可借鉴：** “源码参数相等”“布局框相等”“最终显示没有问题”是三种证据。文本还需要检查换行、基线和裁切，不能仅凭外框数字签收。

### 2.4 社区案例：给宽度加几个像素，只能修好一台设备

[RN #5711：Flex 非整数尺寸产生视觉伪影](https://github.com/react/react-native/issues/5711)

讨论中有人尝试给宽度加 1～3 来规避取整；作者指出，这会在其他屏幕尺寸和方向下再次出问题。该讨论涉及早期 RN，适合作为问题模式的证据，不作为当前框架缺陷结论。

**可借鉴：** 不应要求开发为了某次验收的整数读数，加入没有适配依据的“魔法修正值”。

### 2.5 Zeplin 官方 FAQ：全部尺寸变成一半或两倍

[All the measurements are wrong, half/twice the size!](https://support.zeplin.io/en/articles/377467-all-the-measurements-are-wrong-half-twice-the-size)

Zeplin 明确把这类问题指向项目的设计密度配置。例如，设计在 2x 下的 20px，要转换成 1x 开发基准的 10。设计密度由项目约定，不是目标手机的屏幕密度。

**可借鉴：** “设计稿是 1x / 2x / 3x”与“设备是几倍屏”必须分别配置，不能合成一个含义不清的“缩放比例”。

## 4. 你们需要先确定的三条规则

### 4.1 设计坐标、设备逻辑单位、截图像素分别命名

| 名称 | 含义 | 例子 |
|---|---|---|
| 设计坐标单位 | Figma 文件中的数值；需要声明设计密度及其平台含义 | 375 宽的 1x 画板，间距 16 |
| 设备逻辑单位 | 当前 App 实际布局使用的 pt / dp | 固定 16dp，或等比适配后的 15.36dp |
| 设备渲染/截图像素 | 原生布局映射到渲染像素，以及截图文件中的采样位置 | 3x 下约 48px，或适配后约 46px |
| Mac 画布显示尺寸 | 投屏、缩放后的屏幕展示 | 50% / 100% / 200%；不应改变上述测量结果 |

Android 官方建议用 dp 定义距离和尺寸，并说明 `px = dp × density`；见 [Support different pixel densities](https://developer.android.com/training/multiscreen/screendensities)。Apple 的 [Points Versus Pixels](https://developer.apple.com/library/archive/documentation/WindowsViews/Conceptual/ViewPG_iPhoneOS/WindowsandViews/WindowsandViews.html) 明确说明坐标与距离用浮点 points，不能假设一个 point 等于一个 pixel。Apple 该文是归档文档，只引用其单位模型，不采用其中旧设备尺寸表。

还要注意：视频帧或缩放后的截图不一定与设备渲染像素 1:1。裁剪、旋转、降采样和内容区域偏移要单独记录；不能一律用“截图宽 / 逻辑宽”代替设备真实 density。

### 4.2 先约定适配策略，才能计算当前设备的目标

“设计稿 375 宽，设备 360 宽”并不自动意味着所有尺寸都乘 `360 / 375`。

| 设计意图 | 当前设备上的期望值 | 检查方式 |
|---|---|---|
| 固定尺寸 | 如间距始终 16dp/pt | 比较固定逻辑目标和实测，不按整屏宽反算 |
| 等比适配 | 如项目明确约定 `16 × viewport / 375` | 显示适配后目标，再解释该框架的像素吸附 |
| 弹性/约束布局 | 如左右各留 16，中间内容填满 | 检查边距、对齐和约束；宽度随可用区域变化 |
| 内容驱动 | 如文字自适应宽高、卡片随内容增长 | 检查内容、换行、内边距、最小/最大尺寸和裁切 |

**先由设计与开发认可规则，再检查实现。** 读取源码有助于解释实际链路，但不能把实现里现有的函数自动当成设计标准，否则实现错误也会被复制到“期望值”中。

短期可先选一类参考视口、默认字体大小和稳定页面状态验收。其他视口只有在适配规则明确后再计算目标。即使在参考视口中，仍要处理高倍设计、字体和边界取整。

### 4.3 宽高、元素间距、圆角不共用一个整数化规则

- **布局框宽高：** 保留原生/布局引擎实际矩形。按根坐标计算边界；必要时解释取整前后的差异。`round(right) − round(left)` 与 `round(width)` 可能不同。
- **元素间距：** 明确是哪两个框、哪两条边。两框空隙不一定就是代码的 margin/padding；文字布局框到卡片边缘的距离也不等于字形墨迹到卡片边缘的距离。不能把几何测距直接标成“padding”。
- **圆角：** 检查四角的运行时解析值、适配规则与绘制方式；允许浮点。圆角参数不是一个必然要取整的水平像素距离。Figma 的平滑圆角、平台圆角和自绘路径还可能参数相同而曲线不同，需要人工观察。

仅凭原生矩形通常不能恢复开发最初写的 `width`、margin、padding 或 token；同样的矩形可以由不同约束产生。拿不到原始属性时，应明确显示“布局结果”，不要显示为“源码设置值”。

## 5. 推荐的人工检查界面与判定流程

### 5.1 每次验收先确认一次环境

保存：设计版本、设计密度、参考视口、目标平台、设备逻辑视口、真实 density、系统字体设置、适配策略、截图采样/裁剪信息和 App/SDK 版本。

现有入口已经固定为 Figma 插件导出和 RN SDK 上传，因此这里应由两端协议**自动生成、校验并落盘验收上下文**，不增加每次验收的人工配置步骤。插件上报设计框尺寸、导出倍率和布局属性；SDK 上报平台、窗口尺寸、设备密度及可采集的运行时属性。重点是校验字段完整性和单位，以及确认采集后的元数据被 Mac 持久化保留。

需要区分：插件的 `exportScale` 是 PNG 导出倍率，不等于设计文件本身按 1x/2x 绘制的语义；通用 RN SDK 读到原生布局结果，也不自动知道宿主自定义 `w()` 的设计基准与使用范围。项目如果已有统一约定，应在插件或 SDK 接入时声明一次并随上传传递；对混合适配的属性补充对应规则。由接入协议提供这些信息，而不是让验收人员反复填写或根据数值猜测。

### 5.2 主面板展示设计要求、设备目标、实测结果

示例条件：375 宽 1x 设计、360dp 设备视口、density 3；**双方已约定该尺寸按宽度等比适配，并使用单值最近像素吸附**。

| 检查项 | 设计要求 | 当前设备目标 | 实测示例 | 提示 |
|---|---|---|---|---|
| 元素宽度 | 16 设计单位 | 连续值 15.36dp；按该约定吸附后约 15.3333dp / 46px | 15.3333dp / 46px | 符合本次约定 |
| 固定边距（另一类规则） | 固定 16dp | 16dp / 48px | 16dp / 48px | 不应套用整屏等比公式 |

这里的 46px 是单值吸附示例，不能直接推广到任意根位置的边界差或任意两个元素间的距离。一般元素间距应由已选两条实际边界计算；需要精确解释时，期望边界也要有明确的布局依据。

默认突出目标和实测的逻辑值与单位；展开后再看原始矩形、物理/截图像素和换算步骤。设计人员不应先算一遍公式才能决定是否提问题。

### 5.3 用四类提示辅助人工签收

| 提示 | 条件 | 人工动作 |
|---|---|---|
| 一致 | 在已确认规则下目标与实测一致，或仅有数值计算精度残差 | 检查外观后签收 |
| 栅格差异待确认 | 有明确取整链路能解释的小差异 | 观察是否白缝、裁字、细线异常；确认接受或提问题 |
| 存在偏差 | 超出约定范围、用错适配策略，或出现可见异常 | 记录期望、实测、元素关系和截图，交给开发修复 |
| 信息不足 | 缺属性、规则未确认、两侧框含义不一致、截图空间未知 | 补采集或补规则，不自动通过/失败 |

**不存在本次查证支持的“统一 ±1px 就是行业标准”。** 对最近整数吸附，单个标量相对连续值的误差最多约 0.5 个物理像素；两个独立边界的差值相对连续距离可达到约 1 个物理像素。这只是限定模型下的数学误差，不包含混合预取整、文字特殊处理、裁剪、错误框匹配或截图缩放。

若首版需要筛查阈值，可先将框边界/间距的约 1 个物理像素差异作为“待确认”提示，用真实样本校准；不要自动把这一范围全部签收。对比的目标若已精确包含平台取整，就应检查剩余差异，而不是再重复加同一笔取整容差。圆角、文本和细线分别约定。

切换显示单位和缩放画布时，原始证据与人工签收结论保持不变；计算精度、筛查容差、设计团队接受的偏差也要分别记录。

## 6. 对当前仓库的具体判断

本轮只做调研和只读检查，以下不是已完成的产品修改。

### 6.1 已具备的基础值得保留

- `packages/react-native-ui-acceptance/README.md` 已说明截图与节点同步采集、逻辑/像素坐标约定、圆角读取能力和平台局限。
- `apps/screen-mirror-mac/src/renderer/src/lib/measure.ts` 已有两个矩形之间的 gap/inset 几何测量。
- `comparison.ts`、`pixelProjection.ts` 已把部分显示单位与比较数值分开；缺采集通道也有独立状态。
- `src/types/pixelTransform.ts` 已集中变换，并区分 `presnap` / `raw`。

这些能力足以支撑先做明确适配范围内的人工检查，无须推倒重建。

### 6.2 当前需要澄清的不是再增加一个总比例

1. `comparison.ts` 把尺寸类值换回设计基准，并统一用 `LENGTH_TOLERANCE = 0.5`。这只适合已确认的对应适配策略，不应作为所有固定尺寸、字体、圆角和弹性布局的通用规则。在总倍率 2.88 的例子里，0.5 个设计单位相当于约 1.44 个物理像素，所以不能称其为统一“1px 容差”。
2. `NodeInfoPanel.tsx` 和 `pixelProjection.ts` 的像素显示还会把圆角等标量换算并吸附到整数。界面已有“换算、非实测”的说明，这是好的；但该整数不能作为曲线边缘的实测真值，也不应取代圆角原始逻辑值。
3. 目前按宿主整体选择 `presnap` / `raw`。如果同一页面存在固定值、`w()`、弹性布局、文字和 SVG，自身就可能混合路径。单一档位不足以证明每个元素的精确像素期望。
4. 当前是从原生结果读取大量信息。若用户要判断“开发有没有写对 token / padding”，还需对应的源码属性或布局语义证据，不能只靠最终矩形反推。

### 6.3 旧材料存在需要先纠正的数学与推理问题

`apps/screen-mirror-mac/docs/SIZE-ACCEPTANCE-PITFALLS.md` 的 18 示例写道：

```text
18 × 360 / 375 = 17.28
round(17.28 × 3) / 3 = 17.3333...
17.3333... × 3 = 51  ← 这一行不成立，应为 52
```

同样参数下，`round(18 × 1080 / 375)` 也是 52。仅对这个标量、同一倍率且中间只有该次最近像素吸附时，两种写法在精确算术下等价；不能用它证明“漏掉中间吸附必然从 51 变成 52”。真正的边界取整、其他中间变换和布局分配问题要分别验证。

该文设备表还有：`1080 / 375 = 2.88`，不是 3；`1206 / 375 = 3.216`，不是 2.6866。3 是这两组给定数据的设备 density，并不等于设计到设备像素的总倍率。

另外，“出现分数逻辑尺寸就一定使用了 w()”不能作为通用判据：布局引擎的边界吸附同样可能产生整数像素除以密度后的分数。设计稿有小数，也不意味着经过明确定义的映射后无法验收。

**这些是已核对的文档/注释问题，不能据此断言真机采集错误。** 如果原始记录确实是 51，需要重新确认它测的是哪个元素、哪种属性、当时参数和真实实现链路，而不是用错误算式解释它。本轮不覆盖修改历史材料，以免把待核对的实测事实一并改掉。

## 7. 建议按这个顺序恢复推进

1. **先对齐插件与 SDK 的验收上下文协议。** 自动获取并持久化已有的设计尺寸、导出倍率、平台、视口和密度；核实项目的设计单位与适配规则是否已随上传传递。缺少的项目规则由接入配置一次声明，区分固定、等比、约束和内容驱动；不增加每次验收的人工填表。
2. **先开放“事实检查”。** 用户可以选元素看原始逻辑属性、选两个框看距离；未配置设计映射时，仍可测量并人工记录，不给误导性的自动红绿结论。
3. **加“当前设备目标”列。** 先覆盖规则明确的宽高、边距与四角；未知规则显示原因。优先展示 dp/pt，不把设计原值强行与截图 px 并列比较。
4. **用小样本校准。** 选择整数与非整数 density、参考与非参考视口；包含非零位置、相邻边界、父子框、细线、四角和文本，验证画布缩放不改变读数。样本既要有正确实现，也要有人为改错，才能同时检查误报和漏报。
5. **形成可复核的问题记录。** 保存设计版本、设备环境、两端元素、测量边、目标/实测/差值、证据来源和人工结论。这样后续修复复验才有稳定依据。

优先目标是让设计人员能明确回答：“我检查的是什么、这台设备上应该是多少、实际是多少、这次差异为什么接受或不接受。”

## 8. 调研范围与限制

本次覆盖原生元素检查、Web 设计检查和设计交付单位转换三类方案；未把截图回归或 AI 差异检测当作人工元素验收替代方案。通用搜索引擎部分请求触发验证，资料主要通过可访问的官方文档、官方帮助中心、GitHub issue 和公开源码交叉核实。未读到的产品能力不作“不支持”的断言。

阈值、四类提示和落地顺序为针对当前项目的建议，需要设计与开发用真实样本确认；它们不是竞品公布的统一标准。
