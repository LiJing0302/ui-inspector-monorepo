# UI 验收的像素级难点

> **范围声明**：本文是**方法论**，不绑定任何具体实现或代码库。文中「实测」标注的数字来自  
> 一次真实项目（移动端，Android + iOS 双端，3024 个设计节点 / 35 份真机快照），  
> 仅用于说明难点的普遍性；换项目结论依然成立，因为每条都对应一个**机制性成因**，  
> 不是某个工具的缺陷。
>
> 一句话立论：**像素级验收的难点不在「算得准不准」，而在「同一个数字有几个坐标系、  
> 几次取整、几套渲染管线」必须逐一对齐。** 任何一条没对齐，误差都是 1px 级，  
> 且看起来像「差一点」而非「错了」。

# 第一部分：几何与单位

## 1.1 同一个数字在三个坐标系里含义不同

**现象**：设计稿标注 18，实机量出来不是 18；换一台设备又变了。

**成因**：一份 UI 至少存在三套坐标系，同一个「18」在其中含义互不相通。

| 坐标系   | 单位                    | 谁在用           | 典型值       |
| ----- | --------------------- | ------------- | --------- |
| 设计坐标系 | pt / dp（设计基准，如 375 宽） | 设计工具、标注、间距规范  | `18`      |
| 布局坐标系 | dp（设备逻辑单位）            | 端上代码、布局引擎     | `17.3333` |
| 物理坐标系 | px（设备物理像素）            | 截图、渲染层、实测矩形通道 | `51`      |

**关键认知**：三套之间的转换**不是一次乘法**，至少包含「基准缩放」与「吸附到像素格」两段。  
把三段压成一步乘总倍率，**在倍率恰好整数时可能看不出差别**（实测某设备倍率 3.0，  
一步乘与两段算出的物理像素完全一致），但**倍率不整齐的设备上就会大面积差 1px**  
（见 7.1）。所以「我这里算得对」不能推广到别的设备。

**验收含义**：

- 「设计值 = 实测值」这个命题**原理上不成立**（见 2.3、设计稿本身非整数）。
- 必须先声明「这一次的期望值是在哪个坐标系里」，否则两侧不可比。

## 1.2 缩放基准不统一

**现象**：同一个 `width: 18`，在不同页面/不同容器下落到不同的物理尺寸。

**成因**：项目里通常**同时存在多种缩放工具**，各自基准不同：

| 工具                      | 基准             | 用途     |
| ----------------------- | -------------- | ------ |
| `w(v)` / `scaleWidth`   | 设计宽（如 375）     | 尺寸     |
| `sp(v)` / `scaleHeight` | 设计高（如 667）     | 字号     |
| 字体缩放                    | 系统 `fontScale` | 无障碍字号  |
| 无（裸写设计值）                | —              | 交给布局引擎 |

⚠️ 同一份代码里混用「宽基准」和「高基准」是很常见的错误来源：视觉上差一点点，但逐元素不同。

**验收含义**：判断某个元素的期望值，**必须先确认它走的是哪条缩放路径**，不能只看源码里有没有包缩放函数。

# 第二部分：取整与栅格

## 2.1 取整时机决定 1px（最难）

**现象**：同一矩形，两种「算法上都说得通」的做法差 1px，且**大多数元素上完全一样**，只在特定位置冒出差值。

**成因**：布局引擎有两种取整时机，各自有大量等价实现：

```
方式 A（逐属性吸附）：      宽 = snap(w)              ← 属性之间不互相参照
方式 B（按边界吸附后相减）： 宽 = snap(x+w) − snap(x)   ← 边界之间互相参照
```

**为什么难**：这不是「谁对谁错」，而是**两种宿主类型**（属性级预吸附 vs 布局引擎按绝对边界吸附）的真实差异。  
选错档位会让**正确实现被报成 1px 偏差**，且因为「绝大多数元素相同」，表现为**零星假阳性**而非大面积失败，最难定位。

**实测**：某矩形（宽 32）在 `x=0` 时两档一致，在 `x=38.33` 时分出 1px；宽 351 在 `x=12` 时分出 1px，`x=13` 时又一致。

⚠️ **致命陷阱**：用 `x=0` 做验证，两档**恒等**（`snap(0+w) − snap(0) = snap(w)`），  
会误判成「其中一个分支没生效、档位形同虚设」。**验证差异必须用非零 x。**

## 2.2 吸附函数返回「分数」而非整数

**现象**：把吸附结果当整数用，会丢掉它保留的余量，逐元素偏大（或偏小）1px。

**成因**：主流跨端框架的像素吸附 API 长这样（React Native 为例）：

```js
roundToNearestPixel(layoutSize) {
  const ratio = PixelRatio.get();
  return Math.round(layoutSize * ratio) / ratio;   // 整的是「物理像素」，除回来仍是分数
}
```

它的文档注释写得清清楚楚：`density 3 时 roundToNearestPixel(8.4) = 8.33，对应恰好 8.33 × 3 = 25 像素`。

⚠️ 但它返回的 `8.33` &#x662F;**「已吸附到像素格的逻辑值」**，不是整数。把它当整数会**丢掉 1/3 像素余量**：

| 做法           | `w(32)` 的逻辑值 | 物理                  | 对不对      |
| ------------ | ------------ | ------------------- | -------- |
| 漏掉吸附         | 30.72        | `round(92.16)` = 92 | ✓ **蒙对** |
| **当整数取整**    | 31           | 93                  | ✗        |
| **保留分数（正确）** | 30.6667      | 92                  | ✓        |

**验收含义（两个独立的验证陷阱）**：

- ⚠️ **「漏掉吸附」会蒙对**：`w(32)` 恰好得 92。单个样本无法验证公式，必须**全量扫连续值**  
  （实测 1~400：「当整数取整」有 **256/400 = 64%** 不符）。
- ⚠️ ⚠️ **倍率恰好为 3.0 的设备验不出吸附问题**：实测「漏掉吸附」与「保留分数」的物理结果  
  在 1~400 上**完全一致（0 差异）**。⇒ 要验吸附是否做对，**必须换倍率不整齐的设备**（见 7.1）。

## 2.3 设计稿本身就有大量非整数尺寸

**现象**：期望值算出来是 51.84，而实现只能给整数，判定标准怎么定都不对。

**成因**：设计稿里的宽度并非都是整数。

**实测**：3024 个设计节点矩形宽中，**775 个（25.6%）是非整数**，值域覆盖 0.66 / 9.99 / 18.48 / 93.17 等。

**验收含义**：

- **「设计稿与实机逐像素相等」在原理上就不成立** —— 映射链路上至少两次吸附。
- 容差必须**按物理像素定义**，且要显式写出来（例：`|设计投影 − 实测| ≤ 1px`），不能用「相等」。

## 2.4 「非整数」是单向判据

**现象**：想用「实测值是不是整数」反推某个元素走没走缩放工具。

**成因**：缩放工具的输出**本来就可能是整数**（当 `设计值 × 比例` 恰好为整数时，如 100 → 96、25 → 24）。

**正确的判据方向**：

- ✅ **「实测是 1/3 或 2/3 分数」⇒ 一定经过了缩放工具**（单向可靠）
- ❌ **「实测是整数」⇒ 不能推断没经过缩放工具**（反例：上面那些）

# 第三部分：字体

## 3.1 字体度量是「每平台一套」，不是一套公式

**现象**：同一段文字、同一字号，iOS 与 Android 上的行高、基线、实际占位高度都不同。

**成因**：

- 两端的字体度量、默认行高规则、字形边界盒定义不同。
- **默认字体族不同** ⇒ 同一个 `font-size` 的字形宽高不同。
- Android 上 `Roboto` 与 iOS 上 `San Francisco` 的 x-height、ascender/descender 比例不同。

**验收含义**：字号一致性只能在**同平台内**比较，跨平台比「行高是否一致」没有意义。

## 3.2 字重在两端常常「名义相同、实际不同」

**现象**：`font-weight: 500` 在两端渲染出的粗细肉眼可见不同。

**成因**：

- 两端支持字重档位集合不同（`normal/500/bold` vs 全档位）。
- **字体文件本身不同** ⇒ 同一个字重号映射到不同字形。
- 变体字体（variable font）支持度不同。

**验收含义**：字重应按「**档位是否映射到预期字形**」验收，而不是按「CSS 字重号相等」。

## 3.3 字体回退（fallback）不可控

**现象**：设计稿指定某字体，设备上没装 ⇒ 实际用回退字体渲染，字宽全变，行末换行位置变化。

**成因**：字体未打包 / 未命中，中端到系统默认或用户已装字体。

**验收含义**：这是**环境依赖**而非实现缺陷，验收前必须确认字体可用性；否则字体相关的所有结论都不可靠。

## 3.4 系统字号缩放（无障碍）会整体放大

**现象**：同一份代码在不同用户设置下布局完全不同。

**成因**：系统 `fontScale`（iOS 动态字体 / Android 系统字号）会改变文字占位高度，进而触发重新换行与布局重排。

**验收含义**：

- 必须声明**在哪个字号设置下验收**（通常锁定默认 1.0）。
- 字号缩放下「像素级相等」不可追求，验收标准应降级为「布局不破、不截断、可读」。

## 3.5 文本抗锯齿与次像素渲染让「颜色」不可逐点比

**现象**：文字边缘像素的颜色是前景与背景的混合，无法取到纯前景色。

**成因**：灰度抗锯齿 / 次像素渲染（subpixel AA）会在笔画边缘产生过渡色。

**验收含义**：

- 文字颜色**只能取笔画最浓处的像素**，不能取区域均值。
- 与抗锯齿相关的 ±1 色差是**渲染正常现象**，不是缺陷。

# 第四部分：颜色与图像

## 4.1 颜色有「多套写法」与「多种编码顺序」

**现象**：同一个颜色值在设计工具、代码、CSS 里含义相反。

**成因（最容易出事的两点）**：

1. **8 位hex 的字节序在不同生态里相反**：
   - 移动端原生（Android ARGB / iOS RGBA 转换）：`#AARRGGBB`（alpha 在**首**）
   - Web / CSS / Figma：`#RRGGBBAA`（alpha 在**末**）
   实例：形如 `#8a000000` / `#40000000` 的值
   - 按原生口径 = **黑色 + 不同透明度**（54% / 25%）
   - 按 CSS 口径 = **深红系、透明度 0**
   ⚠️ 这类值不是孤例：某项目一份快照里 258 个 8 位色节点，**去重只有 2 个**，  
   全部是「黑色 + 不同 alpha」⇒ 这是一类问题而非个案。
2. **同一色有多种表达**：`#fff` / `#ffffff` / `#ffffff00` / `rgba(255,255,255,0)` / `hwb()` / 命名色 ⇒ 字符串比对天然不等。

**验收含义**：

- 颜色比对必须**先归一化到同一编码顺序 + 同一表达形式**。
- ⚠️ **归一化不能无条件做**：给设计侧的值套原生侧的字节序，会把 `#ffffffb2`（白 70%）错翻成 `#ffffb2ff` —— 同样致命、方向相反。

## 4.2 半透明色的实际呈现取决于它下面压着什么

**现象**：同一个 `rgba(0,0,0,0.5)`，在白底和图片上是完全不同的观感。

**成因**：Alpha 是**合成**结果，取决于背景。

**验收含义**：半透明色**不能独立断言**，必须连同其下层内容一起采样，或明确约定合成基准。

## 4.3 阴影 / 模糊的判定缺少唯一真值

**现象**：设计稿里阴影是矢量图层，代码里是 `shadow*` 参数，两者的模糊半径、扩散、Y 偏移换算关系不唯一。

**成因**：设计工具的阴影模型与平台的阴影实现参数语义不对齐（尤其 spread 与 blur 的组合）。

**验收含义**：阴影应按「**视觉近似 + 参数可解释**」验收，不宜追求参数逐个相等。

## 4.4 位图资源的缩放采样不可逆

**现象**：设计稿 `@1x` 导出图，在 `@3x` 设备上采样结果与原图不逐像素相同。

**成因**：缩放算法（双线性/Lanczos/浏览器实现差异）+ 色彩空间转换。

**验收含义**：

- 位图区只能做**感知级比对**（结构相似度 / 色差阈值），不能逐像素相等。
- 验收前确认导出的倍率与设备倍率匹配，否则差异是必然的。

## 4.5 矢量资源的缩放规则是另一套

**现象**：SVG / 矢量图标的内部元素尺寸与外框尺寸不成比例。

**成因**：矢量图有自身的 **viewBox 缩放**，内部路径按 viewBox 独立变换，**不经过**页面的尺寸缩放工具。

**验收含义**：

- ⚠️ **这是公式张冠李戴最常见的原因**：矢量图标内部的子节点不适用页面的缩放公式。
- 判定时应识别「外框尺寸走缩放工具」与「内部结构走 viewBox」两层。

# 第五部分：布局与滚动

## 5.1 布局引擎的舍入规则与实现强相关

**现象**：同一份布局描述在不同引擎/版本上结果差 1px。

**成因**：Flex / Grid 的实现里，「子项尺寸先整再排」与「先排再整」在不同版本、不同`flexGrow` 场景下不同。

**验收含义**：期望值必须绑定「引擎 + 版本」，跨版本不保证。

## 5.2 滚动容器的子元素有「未滚到」与「不存在」之分

**现象**：全量采集会把屏幕外/未滚到的内容也采进来，看起来像「元素存在但尺寸为 0」。

**成因**：滚动视图的子节点在未进入视口时仍存在于视图树。

**验收含义**：

- 必须区分「**未参与本次验收**」与「**确定不存在**」—— 这两个结论对验收动作的含义完全相反  
  （前者 = 要补截图，后者 = 要改实现）。
- 判据要用「**完全在视口外**」这类可验证条件，且明确用外框还是可见框（空矩形无法区分「被裁」与「不在场」）。

## 5.3 折叠态 / 展开态是不同布局

**现象**：元素被裁剪到高度 0，但其子节点仍各自报尺寸。

**成因**：折叠通常是 `overflow: hidden` + 高度 0，不是「真的没有」。

**验收含义**：判据必须区分「零尺寸但有子节点」与「零尺寸且无子节点」；前者是**折叠态**，不是噪声。

## 5.4 层级中的容器不是像素

**现象**：把纯布局容器按「可绘制元素」验收，产生大量无意义结论。

**成因**：容器的作用是**树结构**（定位、层级、继承），它本身不贡献像素。

**验收含义**：

- ⚠️ **「有子节点的容器」绝不能剔除** —— 子节点引用它的父子关系，删掉会导致匹配断裂。
- 应区分「零尺寸容器」与「纯布局容器」，且判据要单一实现（画布与列表共用一处）。

# 第六部分：动态内容

## 6.1 数字滚动组件按「位」实例化

**现象**：价格 `¥3599` 在界面上显示为 `3599`，但采集到 4 个独立节点，每个只显示一位。

**成因**：数字轮组件把每一位独立实例化，各占一个容器，靠位移露出当前位。

**验收含义**：

- 逐位比对会把「设计 `¥3599` ↔ App `6`」报成严重错误。
- 正确做法是**把整个数字区域视为一个动态单元**判定。

## 6.2 动画中的中间态不该算作缺陷

**现象**：采集恰好落在过渡帧，尺寸/透明度是中间值。

**验收含义**：验收必须在**稳定态**采集，并在采集前确认无进行中动画。

## 6.3 加载态、骨架屏、空态各有不同结构

**现象**：同一页面在加载完成前后节点树完全不同。

**验收含义**：验收要**声明处于哪个状态**；骨架屏节点不应参与正式验收。

## 6.4 字体回退 / 图片加载失败改变最终布局

**现象**：网络图片未加载时占位尺寸，加载后跳变，导致后续元素位移。

**验收含义**：图片尺寸应在**加载完成后**采集；或约定按占位尺寸验收并说明。

# 第七部分：平台与设备差异

## 7.1 设备倍率组合决定误差幅度

**现象**：同一份代码在两台设备上误差表现差异很大。

**成因**：总倍率 = 物理宽 / 设计基准，不同设备的倍率「整齐程度」不同。

**实测**：

- 设备 A：viewport 360，物理宽 1080 ⇒ 总倍率 **3.0000**（整数友好）
- 设备 B：viewport 402，物理宽 1206 ⇒ 总倍率 **2.6866**（不整齐）

**验收含义**：⚠️ **只用「整数友好」的设备验证换算公式，换到不友好设备很可能对不上**。  
验公式时要挑**倍率不整齐**的设备，那才是压力测试。

## 7.2 系统栏高度属于「不可控差异」

**现象**：状态栏 / 导航栏 / 底部指示条高度因平台、机型、系统版本而异。

**验收含义**：

- 验收对比时应**约定从哪一条边开始量**（安全区内还是全屏）。
- 不约定就会出现整页系统性偏移。

## 7.3 全面屏与圆角/挖孔影响可用区域

**成因**：刘海、挖孔、圆角裁掉真实像素。

**验收含义**：安全区（safe area）必须纳入坐标换算，否则顶部元素系统性偏移。

## 7.4 深色模式 / 反色主题是另一套真值

**现象**：同一套颜色在深浅两套主题下完全不同。

**验收含义**：验收必须**锁定主题**；深浅两套应分别出结论，而不是互相容差。

## 7.5 系统设置（字号、深色、动画开关）都是变量

**现象**：同一台设备不同用户设置下，同一份代码的验收结论不同。

**验收含义**：验收报告要**记录环境快照**（字号倍率、主题、动画开关、系统版本），否则结论不可复现。

# 第八部分：测量与判定

## 8.1 采集通道本身可能不存在

**现象**：想对比物理像素，但采集侧没有这个通道。

**成因**：采集字段是**版本演进**出来的，老快照天然缺失。

**实测**：某项目 35 份快照中，采集日期在引入该字段之后的 4 份覆盖率 100%，之前的 31 份**全部为 0**。

**验收含义**：缺通道要报「**未采集**」，不能：

- 拿逻辑值乘密度**反算**当实测 —— 那会把取整误差包装成「看起来像量到的数」；
- 静默按「确定没有」处理 —— 那是另一句话，会误导结论。

⚠️ 这类留空在**大面积**发生时必须**主动告知**，否则第一反应是「工具坏了」。

## 8.2 缩放基准与档位要落盘，不能靠默认值

**现象**：换宿主/换项目后，期望值算法默默变了，但没人察觉。

**验收含义**：**档位（宿主取整类型）必须进采集元数据**。  
实测某项目 35 份快照中带该字段的为 **0 份**，全部靠默认值兜底 ⇒ 换宿主必然静默算错。

## 8.3 「判定」与「显示」必须分离

**现象**：切到某个读数口径后，满屏假红。

**成因**：把「显示单位切换」误做成了「判定单位切换」。

**验收含义**：

- **判定**用一套基准和容差，**显示**可以是另一套。
- 切换显示口径时，判定结论**必须逐位不变**。这是可验证的硬约束（见 8.5）。

## 8.4 容差要按「取整次数」定义，不是拍脑袋

**现象**：容差给 0.5 还是 1，结论完全不同。

**成因**：误差来源是**若干次取整的叠加**，每次最多 ±0.5 像素。

**验收含义**：容差上限 = 取整次数 × 0.5（物理像素），并**显式写出来**。  
长度类容差还要考虑「绝对值 vs 相对值」两种模式在不同量级下的表现。

## 8.5 改动期望值算法后必须回放人工标注

**现象**：改完换算逻辑，肉眼看没问题，但结论已经变了。

**验收含义**：

1. **改动前**先跑一次人工标注基线并**记录数字**；
2. 改动后跑同一份回放；
3. **结论应逐位不变**（显示变了可以接受，判定变了就是回归）。

⚠️ 这条能挡住「以为只改了显示、实际改了判定」的回归。

## 8.6 别用反推数字去找口径

**现象**：两端对不上时，试图反推「什么倍率能同时解释所有样本」。

**实测教训**：反推出的区间能**自洽解释**样本（如推出「设计基准 377.5」），但真值是 375 —— 得到的是**伪线索**。

**验收含义**：口径不对时，正确顺序是  
**读实现源码复刻公式 → 与实测逐位对账**，  
而不是拿数字反推。反推得到的自洽解释往往只是「误差范围内的任意拟合」。

## 8.7 验证用例必须能区分假设

**现象**：写了个验证，跑出来「两档没差异」，于是得出「分支没生效」的结论。

**成因**：用例参数恰好让两种假设**必然给出相同结果**（例：`x=0` 时两种取整时机恒等）。

**验收含义**：设计验证前先问一句：**这个用例如果假设是错的，它会给出不同结果吗？**

## 收束

把上面 8 部分压成一句可操作的话：

> 像素级验收的本质是**把「设计意图」翻译成「目标坐标系下的期望值」**。  
> 翻译链路上每一步都有合法的舍入、每种宿主都有不同的取整时机、  
> 每个像素通道都有各自的编码顺序。  
> 任何一处没对齐，误差都是 1px 级 —— 而 1px 级误差看起来永远像「差一点」，不像「错了」。

因此：**先证明期望值算法对（源码复刻 + 逐位对账），再讨论容差；  
先锁定环境与坐标口径，再逐字段比对。**  
顺序反了，就会一直在「差 1px」里打转，而那 1px 往往不是实现问题，是口径问题。
